1. ЛЯХОВ Я.П. - ЗАКАЗЧИК И РУКОВОДИТЕЛЬ
Слайды 1-3. Около 2 минут.

[Слайд 1]

Добрый день. Представляем pulse! - приложение для персонального анализа карт osu!standard.

osu! - ритм-игра. Игрок наводится на объекты и нажимает клавиши в нужный момент. Карты требуют разных навыков: где-то нужно быстро наводиться, где-то быстро нажимать, а где-то разбирать сложный ритм.

Наше приложение сравнивает карту с историей конкретного игрока. Оно показывает, какая нагрузка его ждет, оценивает шанс прохождения и ожидаемую точность.

[Слайд 2]

В игре уже есть общая сложность карты в звездах. Но одинаковые звезды не означают одинаковую сложность для каждого человека.

Например, один игрок хорошо справляется с большими прыжками между объектами, но теряется в быстрых сериях нажатий. Для другого все может быть наоборот. По одному числу звезд это не понять.

Поэтому игрок часто выбирает привычные карты или пробует случайные. Наш продукт помогает сделать выбор понятнее: показывает нагрузку карты относительно того, с чем человек уже справлялся.

[Слайд 3]

Основной сценарий простой. Игрок вставляет ссылку на профиль, собирает доступную историю, добавляет карту и получает персональный отчет. Специально наигрывать новые результаты после запуска не нужно.

В отчете есть личные ориентиры по двум базовым навыкам. Aim - наведение на объекты, speed - скорость нажатий. Рядом показаны нагрузка карты и объем истории, по которой получена оценка.

Затем игрок видит прогноз прохождения, ожидаемую точность и график сложных участков.

Заказчик проекта - я, автор идеи. Дальше покажем, как этот сценарий работает в приложении. Передаю слово разработчику.


2. ГАЙФУЛЛИН А.Р. - ПРИЛОЖЕНИЕ И ИНТЕРФЕЙС
Слайды 4-5. Около 2 минут вместе с демо.

[Слайд 4. Открыть сайт]
[http://127.0.0.1:8011/?user=BaffledHedgehog&map=4610937]

На сайте уже загружены профиль BaffledHedgehog и карта для демонстрации. В истории игрока две тысячи сто двадцать два результата.

[Показать выбранную карту и блок персональных навыков]

Общая сложность карты - шесть целых восемнадцать сотых звезды. Теперь посмотрим на личные ориентиры.

По aim ориентир игрока - три целых шестнадцать сотых, нагрузка карты - три целых семнадцать сотых. То есть наведение почти на привычном уровне.

По speed ориентир - две целых шестьдесят две сотых, а нагрузка карты - две целых восемьдесят четыре сотых. Здесь нагрузка на нажатия примерно на восемь целых четыре десятых процента выше ориентира.

Под шкалами видно, откуда взялась оценка: тысяча три полных прохода на шестистах семидесяти двух других картах с теми же модами. Выбранная карта в этот ориентир не входит.

[Прокрутить к прогнозу и графику]

Ниже показаны шанс прохождения и ожидаемая accuracy, то есть игровая точность. Это текущий расчет с учетом сохраненной истории. Подпись объясняет, какой метод используется.

График справа показывает нагрузку по времени. Так можно увидеть короткий сложный участок, который теряется за общей оценкой карты.

[Вернуться к слайду 5]

Для сбора истории нужна одна основная кнопка. Она получает доступные результаты из сети и дополняет их историей этого игрока из найденных клиентов osu!stable и osu!lazer.

Собираются доступные последние и лучшие результаты, а также закрепленные результаты и первые места. Объем зависит от источника. Совпадающие результаты не добавляются повторно, а разные попытки одной карты сохраняются отдельно.

Данные кешируются, поэтому повторный сбор дополняет историю. Для базового сетевого сценария пароль игрока не нужен.

Теперь о том, как из этой истории получается прогноз. Передаю слово участнику, который отвечает за данные и модели.


3. НЕДУГОВ Д. - ДАННЫЕ И ML
Слайды 6-7. Около 2 минут.

[Слайд 6]

У нас две задачи машинного обучения.

Первая - оценить вероятность прохождения карты. Для нее используется логистическая регрессия по истории игрока. Качество вероятностей проверяется по Brier score. Простая точка сравнения - прошлая доля успешных попыток игрока.

Вторая задача - предсказать accuracy полного прохождения. Для нее подключен градиентный бустинг. Он получает пятьдесят шесть признаков карты и более ранней истории игрока.

Среди признаков есть aim, speed, скорость серий, ритм, слайдеры, моды, время появления объектов и пики нагрузки. Поэтому модель учитывает больше информации, чем только общие звезды.

При подготовке данных важно различать виды результатов. Лучшие результаты описывают достижения игрока, но не показывают, сколько раз он до этого проиграл. Поэтому для обучения вероятности прохождения нужны отдельные попытки с известным исходом.

Для accuracy используются результаты полной карты. Точность короткого незавершенного фрагмента не подменяет точность полного прохождения.

[Слайд 7]

На слайде показан результат личного эксперимента для игры без модов, то есть NM.

Проверка включала четыреста три более поздних прохода из двухсот тридцати девяти семейств карт. Новая модель получила среднюю абсолютную ошибку четыре целых тридцать пять сотых процентного пункта. У прежней модели Ridge было четыре целых шестьдесят семь сотых. Это примерно семь процентов уменьшения ошибки.

Для сравнения: простое среднее прошлых проходов дало ошибку пять целых шестьдесят девять сотых пункта.

Процентный пункт здесь - разница между прогнозом и фактом. Например, прогноз девяносто процентов, результат девяносто четыре - ошибка четыре пункта.

Модель обучалась и выбиралась на ранней истории, а проверялась на более поздней. Семейства целевых карт были разделены между обучением и проверкой. При расчете использовалась только история, доступная до соответствующей игры.

Теперь передаю слово участнику, который отвечает за тестирование и документацию.


4. ТЕМИРОВ А.М. - ТЕСТИРОВАНИЕ И ДОКУМЕНТЫ
Слайды 8-10. Около 2 минут.

[Слайд 8]

В полном регрессионном прогоне прошли сто сорок девять тестов. Они проверяют импорт карт и истории, удаление повторов, кеш, персональные шкалы, прогнозы и работу API.

Есть сценарии с корректными и поврежденными файлами. Отдельно проверяется выбор модели по сравнению с простым методом, в том числе на границе равенства метрик.

Результаты прогонов и ответы API сохранены. Это проверка поведения приложения. Качество самого прогноза измерено отдельно на проверочной истории, как показано на предыдущем слайде.

[Слайд 9]

Работу разделили на четыре зоны ответственности.

Ляхов - заказчик, требования и координация. Недугов - данные, признаки и модели. Гайфуллин - приложение, импорт и интерфейс. Моя зона - тестирование, отчеты и документы.

Роли закреплены в RACI. Эта матрица показывает, кто выполняет работу и кто отвечает за ее результат. Список работ и зависимости оформлены в WBS и ProjectLibre.

[Слайд 10]

Передаем рабочее приложение, исходный код, зависимости и документацию. Есть инструкция запуска, инструкция пользователя, описание данных и моделей, тесты и отчеты.

Чистая установка проверена автоматически в новом окружении без личной базы. Также проверили создание резервной копии и запуск восстановленной контрольной базы. Отчет после восстановления совпал.

Таким образом, в комплекте есть все, чтобы запустить приложение, повторить основные проверки и продолжить разработку.
