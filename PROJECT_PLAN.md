# Анализ карт osu! и персональная сложность

Исследование на 29 сентября 2026 года. Начальная область: **osu!standard**. Для mania, taiko и catch нужны отдельные признаки и модели.

**Статус:** первый локальный прототип реализован; запуск и текущие ограничения описаны в [README.md](README.md). Следующая продуктовая гипотеза — не просто советовать карты, а измерять, помогла ли тренировка конкретного паттерна конкретному игроку.

## Короткий вывод

Идея осуществима, но рынок уже занят. Встречаются сервисы, которые анализируют навыки, рекомендуют карты и даже оценивают шанс прохождения. Поэтому продукт стоит строить вокруг измеримого обещания: **«Как именно эта карта с этими модами сыграется у меня сейчас?»**. Результат — вероятность пройти карту с первой попытки, диапазон ожидаемой точности, оценка риска по участкам и причина прогноза. Рекомендации следуют из этого прогноза.

**Вывод:** общая формулировка «ИИ анализирует карту и рекомендует сложность» уже реализуется другими, а ML прогноз pass/accuracy с overlay уже есть у почти точного аналога. Возможная специализация — **проверяемый персональный прогноз**, привязанный к конкретной карте и модам, с анализом трудных отрезков и измерением результата тренировки на последующих попытках. Уникальность этого сочетания на всём рынке исследованием не доказана; её нужно проверять на пользователях и данных.

## Что должно уметь приложение

1. Игрок вводит имя или авторизуется через osu! OAuth. Приложение получает доступные результаты и строит профиль навыков с указанием объёма данных.
2. Игрок вставляет ссылку на карту, выбирает моды и цель: «разминка», «комфортная игра» или «вызов».
3. Экран карты показывает официальные звёзды и отдельно **персональный прогноз**: шанс pass, ожидаемую accuracy с интервалом, главные сложные участки и факторы риска. Пример текста: «На отрезке 1:12–1:27 быстрые бурсты при 220 BPM; на похожих картах у тебя чаще падала точность».
4. Подбор возвращает карты в целевом диапазоне вероятности успеха, с фильтрами по длительности, модам, тегам и уже сыгранным картам.
5. После игры приложение сравнивает прогноз с результатом и обновляет профиль. Пользователь может отметить, насколько карта понравилась: **сложность и музыкальные предпочтения — разные задачи**.

Для первого релиза достаточно ссылки на карту, профиля и рекомендаций. Покадровый анализ реплеев и точные прогнозы по участкам — следующая ступень после появления данных.

## Данные и права

| Источник | Что даёт | Применение и ограничение |
| --- | --- | --- |
| [osu! API v2](https://osu.ppy.sh/docs/) | Профиль, best/recent scores, метаданные карт, поиск, атрибуты сложности с модами | Основной источник для подключённых игроков. Нужны OAuth, кэш и умеренный опрос; документация запрещает массовый сбор score/user/beatmap данных через API. `best` нельзя считать полной историей игрока. |
| [data.ppy.sh](https://data.ppy.sh/) | Архивы `.osu` и выборки результатов, в том числе `performance_osu_random_10000` и `top_10000` | Полезно для локального исследования и прототипирования. [Лицензия](https://data.ppy.sh/LICENCE.txt) **не разрешает автоматически продакшен использование или публичную публикацию данных**; для этого нужно связаться с osu!. |
| [Формат .osu](https://osu.ppy.sh/wiki/en/Client/File_formats/osu_(file_format)) и локальные карты | События, координаты, тайминг, слайдеры, AR/OD/CS/HP | Основа анализа паттернов. Для пользовательской карты можно принять файл от игрока; музыку и пакеты карт не распространять без отдельного основания. |
| [Формат .osr](https://osu.ppy.sh/wiki/en/Client/File_formats/osr_(file_format)) и локальные результаты | Время, позиция курсора, нажатия, моды, итоговая точность | Опциональный импорт с согласия игрока для анализа ошибок по участкам. Для osu!stable есть `scores.db`; импорт из lazer требует отдельной проверки формата и рабочего процесса. |
| [Теги карт osu!](https://osu.ppy.sh/wiki/en/Beatmap/Beatmap_tags) | Метки jumps, streams, tech, reading и др. | Вспомогательные метки для проверки классификатора. Теги пользовательские и покрывают не все карты. |
| Собранные приложением попытки | Пары «игрок, карта, моды, дата, pass, accuracy, misses, combo» и обратная связь | Главное основание для улучшения персональной модели. Хранить с явным согласием, возможностью удаления и без публичной выдачи чужих реплеев. |

Датасет из одних top plays будет сильно смещён к удачным и любимым картам. Для обучения шанса pass нужны также неудачные попытки; если их нет, показывать осторожный прогноз и не выдавать оценку за хорошо измеренную. Данные разных режимов, модов и систем оценки stable/lazer надо разделять или явно учитывать в признаках.

**Состояние прототипа:** локальная логистическая модель обучается автоматически после 40 попыток, 10 разных карт и не менее 8 исходов каждого класса. При проверке целые карты исключаются из обучения, а Brier score сравнивается с прогнозом по доле проходов. Это минимальный внутренний контроль качества; для научно убедимого утверждения о персональной сложности нужны последующие реальные попытки и отдельная временная выборка. В текущей базе приложения 0 попыток, поэтому реальная модель ещё не обучена. Найденный [`osu-skill-predictor`](https://github.com/nayutalienx/osu-skill-predictor) имеет готовые веса, но не указанную лицензию и другой набор входных признаков; его артефакты не используются.

Минимальная запись для обучения: `user_id`, `beatmap_id` или хеш карты, версия карты, `mods`, версия правил/калькулятора, время попытки, `passed`, `accuracy`, `misses`, `max_combo`, источник результата. Признаки игрока рассчитывать **только по попыткам до момента прогнозируемой игры**, иначе тест будет обманчивым.

## Анализ карты и модель

**Признаки карты.** Помимо звёзд и AR/OD/CS/HP: BPM, длина, плотность объектов по окнам, интервалы и расстояния между объектами, углы прыжков, доля бурстов и стримов, ритмическая сложность, слайдеры, пиковая нагрузка и её длительность. Для HD/HR/DT/NC/EZ/HT пересчитать признаки после действия мода. Официальный рейтинг использовать как сильный базовый признак, а не переименовывать в «ИИ оценку».

**Признаки игрока.** Недавние результаты на сходных картах: медианная accuracy, pass rate, устойчивость на длинных картах, поведение при высокой плотности, разных BPM и AR. По немногим попыткам применять сглаживание к общему профилю и показывать широкую неопределённость.

**Порядок моделей.**

1. Базовая линия: статистическая модель по звёздам, модам и недавним результатам игрока. Это даёт честную точку сравнения.
2. Затем CatBoost или другая модель для табличных данных на признаках карты, игрока и их разностях: `P(pass)` и ожидаемая accuracy. Вероятности откалибровать на отдельной выборке.
3. Когда появятся реплеи и достаточно данных: модель по участкам для риска промаха; более сложные эмбеддинги карт или factorization machines проверять только против базовой линии. [Исследование персональной сложности игр](https://arxiv.org/abs/2209.13495) показывает применимость factorization machines, но не доказывает результат именно для osu!.

Языковую модель можно применять для **формулировки объяснений из рассчитанных признаков**. Ей нельзя поручать выдумывать вероятность прохождения или причину промаха без измерений.

**Проверка качества.** Отложить будущие игры игрока по времени; отдельно проверить холодный старт, новые карты, моды и уровни навыка. Метрики: Brier score и калибровка для `P(pass)`, MAE accuracy, доля рекомендаций с заданной сложностью и доля пользователей, согласившихся с оценкой. Сравнивать с простым прогнозом по звёздам и текущей статистике игрока. Повторные попытки одной карты не должны попадать в обучение при проверке первого прохождения.

## Предлагаемая архитектура

```text
osu! API / импорт .osu и .osr
             ↓
     загрузка и нормализация ──→ PostgreSQL: игроки, карты, попытки
             ↓
     расчёт признаков карт и профилей игроков
             ↓
     baseline → обученная модель → калибровка вероятностей
             ↓
       API прогноза и подбора → веб-интерфейс
```

Стек первого релиза: Python + FastAPI, PostgreSQL, `ossapi`, `rosu-pp-py`, CatBoost, простой веб-интерфейс на React/Next.js. Расчёт признаков карт выполнять фоновым заданием и кэшировать по хешу `.osu`, комбинации модов и версии алгоритма. Rust сервис нужен только если Python реализация окажется узким местом; `rosu-map` можно использовать позже.

## Этапы

1. **Проверка данных.** Уточнить правила использования источников; собрать небольшой локальный исследовательский набор карт и попыток, проверить покрытие неудачных игр и доступность `.osu` для сценария по ссылке.
2. **Вертикальный прототип.** Подключение пользователя, одна карта, корректный расчёт звёзд и модов, базовый персональный прогноз с пояснением источников данных.
3. **Валидация.** Собрать добровольные будущие попытки, измерить калибровку и улучшение относительно рейтинга звёзд. Если улучшения нет — исправить данные и признаки до расширения UI.
4. **Рекомендации.** Подбирать карты под целевой диапазон вероятности и предпочтения, собирать обратную связь.
5. **Анализ участков.** Импорт реплеев, привязка ошибок к паттернам, персональные рекомендации для тренировки конкретного места.

Главное решение перед кодом: подтвердить **osu!standard** как первый режим и выбрать формат первого продукта — веб-сервис по ссылке на карту или локальное приложение с доступом к библиотеке карт и реплеям. По умолчанию этот план предполагает веб-сервис с необязательным импортом файлов.
