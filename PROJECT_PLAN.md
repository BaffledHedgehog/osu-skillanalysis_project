# План проекта pulse!

Студенческий проект Университета Иннополис. Дата: 03.10.2026.

## Задача

Звезды osu! показывают общую сложность карты. Они не учитывают навыки конкретного игрока. Цель проекта - оценить шанс прохождения выбранной карты и показать, где возникают основные нагрузки.

Первый режим - osu!standard. Для других режимов понадобятся отдельные признаки и модели.

## Текущая версия

Давность результатов учитывается в ML и в персональной истории: полураспад базового веса 60 дней, ограничение суммарного веса недели, обновление модели по дням. Прогресс сравнивается на одинаковых версиях карт с одинаковыми модами. Для NF добавлено воспроизведение реплея официальным движком с графиком HP, моментом срабатывания условия провала и проверкой совпадения статистики. Результат расчета хранится отдельно от реально сыгранных попыток.

Обновление импорта: в lazer исход берется из Rank, включая F у неполных попыток. Сохраненные локальные записи уточняются без дубликатов. NF хранится отдельно и не обучает обычный pass. В признаки добавлены пики нагрузки и сложность финала. Прогноз выбранной карты уточняется по ее сохраненным попыткам с теми же модами; это отдельная статистическая оценка, пока без проверки качества на будущих играх.

Обновление от 24.10.2026: жесткие личные пределы отменены. Модель обучается на признаках скорости серий, AR, ритма и Hidden, включая нелинейные связи. Вне наблюдавшегося диапазона шанс отмечается неизвестным. Для сложных карт добавлен подбор более простых похожих карт с прогнозом accuracy от 95%. Добавлен веб-доступ через relay с расчетами на ПК, отдельной базой и блокировкой локальных функций. Постоянный хостинг с личными кабинетами остается следующим этапом.

Обновление от 24.10.2026: добавлен локальный импорт stable и lazer, включая перенесенное хранилище lazer. Импорт cookie остается необязательным. История дополняется без повторных записей, расчеты кешируются по версии данных. Локальные записи без подтвержденного pass не входят в модель прохождения. Расширение до 16 групп навыков идет по этапам из [SKILLSETS.md](SKILLSETS.md).

1. Игрок вставляет ссылку на профиль osu!. Приложение получает recent и best scores без входа в аккаунт.
2. Игрок выбирает карту и моды. Приложение рассчитывает параметры карты и нагрузку по участкам.
3. Приложение строит профиль по результатам и показывает прогноз прохождения и точности.
4. После новой игры игрок может добавить результат вручную или импортировать `.osr`.

Прототип работает локально. Сервер написан на FastAPI. Данные лежат в SQLite. Интерфейс сделан на HTML, CSS и JavaScript.

В списках импорта карты не повторяются. В истории сохраняются разные попытки одной карты, а одинаковый score из recent и best хранится один раз с источником recent. Best scores нужны для оценки достигнутого уровня и PP. Для обучения шанса прохождения они не подходят: все они отобраны по успешности.

## Сбор датасета для своих моделей

### Что считать записью

Одна строка - одна попытка сыграть карту. Повторные попытки сохраняются. Совпадение одного результата в recent и best убирается по `score_id`, но разные результаты на той же карте остаются. Текущий импорт убирает повторы карт внутри загрузки. Для датасета нужна отдельная таблица сырых попыток, а каталог и профиль могут дальше показывать одну запись на карту.

Минимальные поля: постоянный случайный идентификатор игрока, ID результата или хеш локальной записи, ID карты, MD5 файла `.osu`, время попытки, режим, моды, `passed`, точность, промахи и источник. Для каждой строки нужно сохранить версию схемы и способ получения метки. Признаки карты считаются по той же версии `.osu` и с теми же модами. Признаки игрока считаются только по попыткам до этой игры.

### Откуда брать данные

1. С согласия игрока импортировать recent scores по ссылке на профиль. Нужны также неудачные попытки. Повторять импорт после игровых сессий и сохранять новые `score_id`, пока записи не ушли из последних 100. Best scores использовать для стартовой оценки уровня и PP, но не как выборку для обучения `P(pass)`. Частоту запросов держать низкой и кэшировать ответы.
2. Сделать импорт локального `scores.db` из osu!stable. По [описанию формата](https://github.com/ppy/osu/wiki/Legacy-database-file-structure#scoresdb) там есть несколько результатов на одну карту, их время, моды и MD5 карты. Для сопоставления с картой нужен соответствующий `.osu` или каталог `osu!.db`. Для первого прототипа можно проверить [osu-tools](https://pypi.org/project/osu-tools/) и [osu-stable-db](https://github.com/zzzzv/osu-stable-db), но поддержку старых и новых версий файла надо испытать отдельно. Отсутствие результата в `scores.db` не означает неудачную попытку.
3. Предложить добровольцам добавить свои `.osr` и `scores.db`. Импортировать их по явному действию игрока, отмечать версию клиента и оставлять исходные файлы у владельца, если для обучения достаточно таблицы признаков. Реплей нужен для анализа участков карты, но метку `passed` надо получать из надежного источника или спрашивать у игрока.

Открытые `scores.db` нашлись как одиночные примеры. Проверенной коллекции файлов многих игроков для обучения пока нет. Основной путь для такого источника - добровольная передача файлов участниками проекта. `scores.db` хранит локальные результаты и не дает полную историю всех неудачных попыток, поэтому для меток `passed=0` нужны recent scores с неудачами или отдельный сбор после игры.

### Подготовка и проверка

Сначала проверить режим osu!standard, время, моды, MD5 карты и уникальность результата. Отдельно посчитать число игроков, карт, попыток, неудач, повторов и строк без доступного `.osu`. Не смешивать результаты с No Fail и нестандартной скоростью с обычными попытками без отдельного учета модов.

Первая метка - `passed`. Точность лучше прогнозировать отдельно для пройденных карт: точность на сорванной попытке описывает только сыгранную часть. Для прогноза сложных участков нужны реплеи и сопоставление действий с объектами карты. Это отдельный датасет.

Последние по времени попытки каждого игрока оставить для проверки. Дополнительно проверить модель на новых игроках и новых картах. В признаки не включать PP и точность целевой попытки или статистику игрока, посчитанную после нее. Сравнить модель с простым прогнозом по звездам и прошлой доле проходов; считать Brier score и калибровку.

### Порядок работы

1. Добавить таблицу сырых попыток и сохранить все recent результаты, включая повторные игры на одной карте.
2. Сделать импорт `scores.db` и проверить старый и новый формат на найденных примерах. Затем испытать его на файлах добровольцев и сверить число и поля результатов с локальным списком игры.
3. Собрать пилотный набор из разных уровней игроков. Ориентир для первого эксперимента - несколько тысяч попыток с достаточным числом неудач, а не только лучшие игры.
4. Обучить общую модель, проверить ее на будущих попытках и только потом добавить персональную настройку.

## Модель

### Эксперимент: последовательности паттернов и аугментации

CNN реализована на PyTorch и подключается к прогнозу по результатам отдельной проверки каждого выхода. Обучение запускается кнопкой "CNN: паттерны карты и обучение" или из командной строки. Веса, данные эксперимента и отчеты хранятся локально в .data/cnn и не попадают в git.

1. Представить карту последовательностью объектов: интервалы времени с учетом скорости модов, относительные координаты и расстояния, углы, тип объекта, длительность и геометрия слайдера, параметры AR/OD/CS/HP. Интервал времени обязателен: одинаковое число нот может занимать разное время.
2. Проверить 1D-CNN или TCN с несколькими размерами контекста. Обучаемые фильтры могут находить повторяющиеся прыжки, серии и смены направления. Это предположение о полезном представлении карты, а не доказанная модель мышечной памяти игрока.
3. Общий кодировщик описывает паттерны. Отдельная персональная часть получает историю игрока с учетом давности и модов. Выходы - прогнозы ошибок по участкам, accuracy и риска провала. Усреднение по всей карте не должно скрывать короткий сложный финал.
4. Не размечать все окна проваленной карты как неудачные. По реплею получать попадания, промахи, ошибки слайдеров, время события и HP. Глобальный F сам по себе не объясняет, на каком паттерне была ошибка.
5. Для аугментации использовать четыре варианта: оригинал, X, Y и XY. Формулы: x' = 512 - x и y' = 384 - y. XY применяет обе формулы. Другие преобразования и произвольные повороты не добавлять.
6. Отражать все точки слайдеров. Для парного примера с реплеем отражать и координаты курсора. Не менять временные метки, кнопки, параметры модов и метаданные реальной попытки. Не обрезать координаты по границам поля.
7. В обучении все четыре варианта сохраняют метки исходной попытки. Сравнить модели с каждым отражением, всеми четырьмя вариантами и без отражений при одинаковом числе шагов. Предобучение использует только оригиналы, чтобы контроль без аугментации не получил отражения заранее.
8. Аугментации создавать только внутри обучающей выборки после разделения данных. Оригинал, его зеркала и все окна одной карты должны оставаться в одной группе. Учитывать близкие версии карт. Зеркало не становится новой реальной игрой и не увеличивает счетчик независимых попыток.
9. При нехватке размеченных попыток начать с предобучения на картах без результатов, например восстановления скрытых признаков объектов. Затем обучать персональные выходы на реальных попытках. Проверочные карты не использовать в предобучении при заявленной проверке на новых картах.
10. На неизменной проверочной выборке сравнить текущую модель, CNN без аугментаций и CNN с каждым отражением отдельно. Считать Brier score, калибровку и MAE, отдельно смотреть HD, диапазоны AR и карты с короткими пиками. Улучшение проверять и на следующих играх. Если новый вариант хуже, не включать его в основной расчет.

Основная библиотека для эксперимента - [PyTorch Conv1d](https://docs.pytorch.org/docs/stable/generated/torch.nn.Conv1d.html). Основа архитектуры: [TCN для последовательностей](https://arxiv.org/abs/1803.01271). Геометрия поля: [osu! Playfield](https://osu.ppy.sh/wiki/en/Client/Playfield). Отражения в игре: [Mirror](https://osu.ppy.sh/wiki/en/Gameplay/Game_modifier/Mirror_(lazer)).

Реализованный эксперимент: 42 признака каждой ноты, окна по 128 нот с шагом 64, три сверточных блока и объединение среднего, максимума и обучаемых весов окон. Профиль игрока для каждой попытки строится только по более ранним результатам из обучающих семейств песен. Модель восстанавливает скрытые признаки нот при предобучении и обучается прогнозировать pass и accuracy всей карты. Локальный F не переносится на все окна карты.

Данные делятся по семействам песен на 60/20/20 до аугментаций. Одна песня, ее сложности и точные копии паттернов остаются в одной части. Validation выбирает вариант модели, test проверяет выбранный вариант. Для pass нужны хотя бы 8 проходов и 8 провалов в test. Для accuracy нужны 40 полных проходов. Улучшение проверяется повторными выборками целых семейств песен. Веса сохраняются как числовой NPZ без pickle; загрузка проверяет хеш и размеры.

Проверка 24.10.2026: 1680 реальных попыток, 695 семейств. CNN accuracy: MAE 5.49 п.п. против 5.91 п.п. у контрольной модели с тем же профилем и разделением данных. Выбран вариант без отражений. Это результат сравнения, отражения остаются доступны в обучении. CNN pass не подключена: в test только 5 провалов, улучшение не подтверждено. Эти цифры нельзя напрямую сравнивать с прежней проверкой Ridge на другом разделении данных.

Для ошибок по участкам реализована отдельная CNN с тем же типом кодировщика. Официальный движок воспроизводит полный реплей и возвращает события попаданий, тиков, промахов, комбо и HP. В обучение входят только записи с совпавшей статистикой и сопоставлением всех объектов. Неигранный остаток проваленной карты не получает метки промахов.

Два локальных выхода: промах или срыв комбо; попадание ниже 300 на круге или голове слайдера. Это наблюдаемые события, а не диагноз навыка игрока. Итоговая оценка слайдера не считается доказательством ошибки тайминга. Метки сохраняются у всех четырех отражений. Перекрывающиеся окна сводятся обратно к одному прогнозу на исходную ноту.

Локальный эксперимент сравнивает оригинал и четыре варианта вместе с регрессией по признакам ноты и профилю. Семейства песен разделены до обучения, профиль использует только более ранние результаты обучающих семейств. Проверка учитывает каждую попытку с учетом давности, повторная выборка идет по семействам песен. Выход подключается только при улучшении на validation и test и достаточном числе независимых примеров. Обучаемые веса объединения окон сами по себе не являются вероятностями ошибок. Для следующих игр нужны новые наблюдения после выпуска модели.

Эксперимент по участкам 24.10.2026: 120 реплеев отобраны без учета результата, 108 прошли сверку. В обучение вошли 67, в validation 20, в test 21 реплей из 20 семейств. Brier для промахов и комбо: 0.03678 у CNN против 0.03714 у регрессии. Для попаданий ниже 300: 0.17644 против 0.18054. В обоих случаях лучше оригинал без отражений. Общая разница подтверждена повторными выборками семейств, но отдельные проверки NM и CL пока не дают надежного улучшения. Поэтому локальные выходы не подключены. Веса и отчет сохранены, повторная проверка на CPU прошла.

Перед каждым новым бинарным файлом обработчика выполняется проверка отключения звука без реплея. При ошибке обработка не начинается. Для пакетного сбора используется один процесс. Кнопка остановки завершает только задачу выбранного игрока в этой базе и ее дочерние процессы.

Признаки карты: звезды, aim, speed, AR, OD и длина. Начальный прогноз опирается на похожие карты и недавние игры.

После накопления данных обучается логистическая регрессия для `P(pass)`. Условия: 40 попыток, 10 карт, 8 проходов и 8 неудач. Для проверки целые карты исключаются из обучения. Метрика - Brier score. Если модель хуже оценки по общей доле проходов, приложение оставляет начальный прогноз.

Для accuracy подключена отдельная линейная модель Ridge. Она обучается на пройденных попытках (от 40 результатов и 10 карт), а при их нехватке - отдельно на best. Режим best явно помечен: он оценивает удачную игру и смещен к лучшим результатам. Обычные попытки и best не смешиваются в одной обучающей выборке accuracy.

Проверка проходит на 25 процентах карт, исключенных из обучения, с фиксированным разделением и параметрами. Модель должна улучшить MAE относительно среднего accuracy на обучающей части. На картах вне диапазона звезд истории используется предварительная оценка. Интервал accuracy строится по ошибкам на проверке и не является статистической гарантией.

Эксперимент 24.10.2026: профиль baffledhedgehog, 97 best, 25 карт вне обучения. MAE Ridge - 1.88 п.п., среднего - 2.64 п.п. Модель сохранена в JSON и подключена к расчету accuracy. Это внутренняя проверка; прогноз на будущих играх пока не проверен.

## Проверка результата

Для CNN реализована проверка сохраненной модели на попытках после ее создания. Кнопка в окне обучения и команда app.sequence_forward не переобучают модель и не меняют решение о подключении. Контекст каждой новой попытки содержит только более раннюю историю обучающих семейств. При отсутствии новых игр сохраняется статус awaiting_new_plays. Для текущей модели таких игр пока нет.

1. Собрать добровольные попытки после выдачи прогноза.
2. Сравнить вероятность с фактическими проходами. Посчитать Brier score и калибровку.
3. Проверить новые карты отдельно от карт из обучения.
4. Сравнить подбор с простым выбором по звездам.

Тестовый набор в репозитории проверяет код. Он не подтверждает точность прогноза на реальных игроках.
